# `SECURE_put_char_uart` — TrustZone Call Chain

MCU: STM32H563ZIT6 (Cortex-M33, TrustZone enabled)
Board: NUCLEO-H563ZI

This document traces a single character write from NonSecure (NS) firmware all the way through
the TrustZone boundary to the UART peripheral on the Secure side. Each step includes the
disassembly and an explanation of what the hardware is doing and why.

---

## Background: How the CPU Knows What Is Secure

Before looking at the call chain, it helps to understand how the CPU enforces the boundary at all.

On the STM32H5 there are two cooperating layers:

**Option bytes (flash watermark — SECWM registers).** These are burned into the chip before
deployment and define which flash pages are Secure. The flash controller enforces them in hardware
regardless of what software does. On this chip, the `0x0C00_0000` address range is a hardwired
Secure alias of flash — the IDAU (Implementation Defined Attribution Unit, ST's silicon-level
security layer) always marks it Secure, independent of any software configuration.

**SAU (Security Attribution Unit).** The Secure firmware programs this at startup to carve up
the rest of the address space — Secure SRAM, Secure peripherals, and the Non-Secure Callable
(NSC) region where the gateways live. Together, the IDAU and SAU give every address a security
attribute that the CPU checks on every instruction fetch and memory access.

With that in place, the hardware can enforce three guarantees relevant to this call:

1. **NS cannot branch into Secure code at an arbitrary address.** Any NS→S branch must land on
   an `sg` (Secure Gateway) instruction or the CPU raises a SecureFault (`INVEP` — Invalid Entry
   Point) before executing anything at the target.

2. **NS cannot read or write Secure RAM.** Every memory transaction goes through the SAU/IDAU
   attribution check. If NS code dereferences a pointer into Secure SRAM, the bus blocks the
   transaction and raises a SecureFault (`AUVIOL` — Attribution Unit Violation). The memory cells
   are never touched.

3. **Secure code cannot accidentally return to a Secure address using the NS-return instruction.**
   The `bxns` instruction (used at the end of every secure entry point) raises a SecureFault
   (`INVTRAN` — Invalid Transition) if the return address is in Secure memory. This matters for
   calling conventions and is covered at the end of this document.

## Step 2: NS Veneer — `__SECURE_put_char_uart_veneer` (NS image, `0x0810_1730`)

```
08101730 <__SECURE_put_char_uart_veneer>:
 8101730:  f85f f000   ldr.w  pc, [pc]         ; load address from literal pool into PC
 8101734:  0c0fe001    .word  0x0c0fe001        ; literal: 0x0c0fe000 | 1 (Thumb bit)
```

This two-instruction trampoline is generated by the linker from the Secure import library. It is
the only piece of TZ-aware code on the NS side.

**Why `ldr.w pc, [pc]` instead of `b.w`?**

`ldr.w pc, [src]` is a load from memory into the program counter. On ARM, PC is just a general
register (`r15`), and writing any value to it causes the CPU to jump there immediately. In C
terms it is equivalent to:

```c
uintptr_t target = *(uintptr_t *)current_pc;  // dereference the literal pool
pc = target;                                   // jump
```

In Thumb-2, when the instruction at `0x8101730` is executing, PC has already advanced to
`0x8101734` (current address + 4, standard ARM pipeline behaviour). So `[pc]` reads the word at
`0x8101734`, which is the `.word` on the very next line: `0x0c0fe001`.

That value is written into PC, causing a jump to `0x0c0fe000` (bit 0 is stripped and used to
confirm Thumb mode, not as part of the address — this is standard ARM calling convention).

A direct `b.w` instruction cannot be used here because it encodes a *relative* offset and only
has room for approximately ±16 MB of range. NS flash sits at `0x0810_1730` and the Secure
gateway is at `0x0c0f_e000` — a gap of ~83 MB. The literal pool trick is how ARM encodes an
absolute branch to any 32-bit address.

**When does the security state switch?**

The moment the CPU resolves the branch destination to `0x0c0fe000` it consults the SAU/IDAU,
sees a Secure address, and initiates an NS→S transition. Before executing the first instruction
at the target it checks that the instruction is `sg`. If it is not, it raises a SecureFault
(`INVEP`) without executing anything. This is the hardware guarantee that NS code cannot jump
into the middle of a Secure function.

## Step 3: Secure Gateway — `SECURE_put_char_uart` (S image, `0x0c0f_e000`)

```
0c0fe000 <SECURE_put_char_uart>:
 c0fe000:  e97f e97f   sg
 c0fe004:  f70a bc4a   b.w    c00889c <__acle_se_SECURE_put_char_uart>
```

**`sg` — `e97f e97f`**

`e97f e97f` is the fixed machine-code encoding of the `sg` (Secure Gateway) instruction. It
takes no operands, so the encoding is always the same constant regardless of where it appears —
unlike `b.w`, which encodes a variable destination offset into its bits.

`sg` does two things atomically:
1. Verifies the call arrived from NS state. If Secure code executes `sg`, it faults immediately
   (this prevents NS from constructing a fake call by jumping into Secure code that happens to
   contain an `sg` further in).
2. Completes the security state switch. The CPU officially transitions to Secure state, applies
   Secure MPU/SAU rules, and sets up the exception return state so that `bxns` at the end will
   correctly return to NS.

**`b.w c00889c` — `f70a bc4a`**

This is a standard unconditional branch to the actual implementation. `b.w` is the 32-bit wide
Thumb-2 branch encoding. The bytes `f70a bc4a` encode a PC-relative signed offset:

```
target - (instruction_address + 4) = 0x0c00889c - 0x0c0fe008 = -0x0F756C (~1 MB back)
```

That offset is split across bit-fields in the two halfwords `f70a` and `bc4a`, which is why
there is no obvious pattern to the bytes — it is a signed integer spread across non-contiguous
bits per the Thumb-2 encoding rules. The disassembler already decoded it to the human-readable
`b.w c00889c`.

**Register scrubbing**

Before returning, the compiler-generated CMSE epilogue overwrites every register that is not
used to carry the return value:
- `r1`–`r3` are overwritten with `lr` (an arbitrary poison value)
- `s0`–`s15` (the FP caller-saved registers) are each set to `1.0`
- `FPSCR` status bits are masked to remove anything sensitive

This prevents the Secure implementation from accidentally leaking data to the NS caller through
registers it did not intentionally return. The return value (`r0`) is the only register left
intact.

**`bxns lr` — returning to NS**

The epilogue closes with `bxns lr` (Branch eXchange Non-Secure) rather than the usual `bx lr`.
The `ns` suffix is what causes the CPU to switch back to NS state on the return. Without it the
return would stay in Secure state and NS code would resume executing with Secure privileges —
a critical bug. `bxns` with a Secure address in `lr` raises a SecureFault (`INVTRAN`), which
leads into the next topic.

The UART handle lives at `0x3000_0088` in Secure SRAM. The SAU marks this region Secure, so any
attempt by NS code to dereference that address directly would be blocked by the bus before
reaching the RAM cells and would raise a SecureFault (`AUVIOL`).

## Pitfall: Calling `SECURE_put_char_uart` from Secure Code

Given that two symbols exist — the public gateway `SECURE_put_char_uart` and the implementation
`__acle_se_SECURE_put_char_uart` — a natural question is whether Secure firmware can simply call
`SECURE_put_char_uart()` in C and have the linker do the right thing.

It cannot. The linker resolves `SECURE_put_char_uart` to the gateway at `0x0c0fe000`. Execution
proceeds as follows:

1. `sg` — executes as a **NOP** when the CPU is already in Secure state (no fault here)
2. `b.w __acle_se_SECURE_put_char_uart` — branches into the implementation normally
3. Function body runs
4. `bxns lr` — **SecureFault (`INVTRAN`)**, because `lr` holds a Secure return address and
   `bxns` refuses to perform a "transition to Non-Secure" when the destination is Secure memory

The fault does not occur at the call site. It occurs at the return, which makes it an awkward
bug to diagnose without knowing to look for it.

**The fix** is to never call a `cmse_nonsecure_entry` function by its public name from Secure
code. Two patterns work:

Option 1 — call the underlying implementation directly:

```c
// Secure code calls this, not SECURE_put_char_uart
__io_putchar(ch);
```

Option 2 — factor the body into a plain internal function and have both the gateway and Secure
callers use it:

```c
static void put_char_uart_impl(int ch) {
    __io_putchar(ch);
}

int __attribute__((cmse_nonsecure_entry)) SECURE_put_char_uart(int ch) {
    put_char_uart_impl(ch);
}

// Elsewhere in Secure code:
put_char_uart_impl(ch);   // safe — no bxns
```

The `__acle_se_` prefixed symbol technically exists and is callable by that mangled name from
Secure code, but calling it hits the same `bxns lr` and produces the same fault. Option 1 or 2
is the correct solution.
